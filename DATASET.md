# Dataset Documentation

## Source

Dataset sourced from Roboflow Universe — an open-access pallet detection dataset:

- **Dataset:** "pallet" by David Akhihero
- **URL:** https://universe.roboflow.com/david-akhihero-pvxdr/pallet-dezmj
- **Version:** 6
- **Format:** YOLOv8 (normalised bounding boxes: `class cx cy w h`)
- **Exported via:** Roboflow API (downloaded in Google Colab notebook)

The assignment specified two sample datasets on Roboflow (`plh-c-1-veibf` and `pallet-ff5lh-fp7tw`). After review, the `pallet-dezmj` dataset was chosen because it had the most images (519), clean annotations, and a single well-defined `pallet` class matching our use case.

## Why This Data

- No real warehouse dataset was available. The assignment explicitly states: "No dataset is provided. Sourcing it is part of the work."
- Roboflow Universe hosts community-pallet images that are already annotated in YOLOv8 format — ready for training without additional labelling time.
- The dataset contains pallet images in various warehouse-like settings with bounding-box annotations.
- **Cost of this choice:**
  - Images do not match the exact camera angle (1.2m height, 20° tilt) described in the problem. Lighting, background, and pallet types may differ from a real Delhivery warehouse.
  - Only bounding box annotations are available — no keypoint (corner) annotations. This meant corners had to be estimated from the bounding box at inference time, introducing pose error.
  - Limited geographic diversity — images may not be from Indian warehouses.

## Class and Annotation Counts

| Dataset | Images | Annotations | Classes |
|---------|--------|--------------|---------|
| pallet-dezmj (v6) | 519 | 519 (1 per image) | pallet |

- **Class:** `pallet` (single class)
- **Annotation type:** Bounding box only (`[x1, y1, x2, y2]` + confidence)
- **No keypoint annotations** — 4 pallet corners are estimated from the bounding box at inference time (5% inset). This is the single biggest limitation in the pipeline.

## Annotation Format

- **Format:** YOLOv8 (normalised bounding boxes: `class cx cy w h`)
- **Coordinate system:** Normalised to image dimensions (0.0–1.0)
- **Label file:** One `.txt` file per image, one row per annotation
- **`data.yaml`:** Class names and paths, generated by Roboflow export

## Split Protocol

- **Split ratio:** 70% train / 15% val / 15% test
- **Split method:** Random (dataset does not contain location or scene metadata for grouped splits)
- **Declaration:** The held-out test set contains images not seen during training or validation. The split was performed by the `prepare_dataset.py` script using a fixed random seed for reproducibility.
- **What differs from training:** The test set was drawn randomly from the same distribution as training data. A stricter test (e.g. images from a different warehouse or camera angle) would better evaluate generalisation, but no such metadata was available.

## Labelling Guideline (One Page)

See `docs/labelling_guideline.md` for the full one-page labelling guide.

**Summary:**

### Pallet Bounding Box
- Draw tightly around the **entire visible pallet** — deck boards + visible stringers.
- Do not include the load (boxes/wrap) inside the pallet box.
- If the pallet is partially occluded, label the visible portion.

### Pallet Corners (Keypoints — for Pose Estimation)
- Mark the 4 corners of the pallet **top surface** (the deck). Order is clockwise:
  1. Top-left corner
  2. Top-right corner
  3. Bottom-right corner
  4. Bottom-left corner
- If a corner is occluded, mark it as `visible=false`.
- **Note:** The current dataset does NOT have keypoint annotations. The above is the guideline that would be used if labelling corners. In this submission, corners are estimated from the bounding box.

### Quality Rules
- One labeller for consistency.
- Ambiguous cases (heavy occlusion, poor lighting) flagged.
- At least 10% of labels double-checked.

## Training Decisions

- **Model:** YOLOv8s (Small) — 11.1M parameters, 28.4 GFLOPs
- **Why YOLOv8s:** Good accuracy/speed tradeoff. YOLOv8n (nano) was considered for speed but sacrificed too much accuracy. YOLOv8m (medium) was too slow for the 15 FPS deployment target.
- **Epochs:** 150, with early stopping at patience=30
- **Batch size:** 16 (reduced to 8 if OOM on Colab T4)
- **Image size:** 640×640
- **Hardware:** Google Colab, Tesla T4 GPU
- **Augmentation:** Default YOLOv8 augmentations (mosaic, mixup, HSV shifts, flip)
- **Why not YOLOv8-pose:** The dataset only has bounding box labels, not keypoints. Training a pose model would require annotating 4 corners per pallet across 519 images (~4-6 hours of manual work). A bbox-to-corner fallback was implemented instead.

## Detection and Localisation Accuracy

**Detection accuracy** (from Colab training — `model.val()` on test split):
- mAP@0.5: reported in training notebook output
- mAP@0.5:0.95: reported in training notebook output
- Precision: reported in training notebook output
- Recall: reported in training notebook output

**Localisation accuracy** (bbox-only, no keypoints):
- Detection confidence on test image: 0.56
- Bounding box: `[110, 98, 199, 193]` pixels
- Corner estimation: 5% inset from bbox edges — introduces ~5-15px error per corner compared to true pallet corners
- Pose translation error: median 2.41cm, mean 3.97cm (synthetic evaluation)
- Pose rotation error: median 0.27°, mean 0.39° (synthetic evaluation)

Detection and localisation are reported **separately**:
- Detection = bounding box mAP (how well the model finds pallets)
- Localisation = pose error (how accurately the corners produce metric position)

## Accuracy Ceiling Estimate

Given 519 training images with bounding box annotations:

- **Detection ceiling:** ~60-70% mAP@0.5. The Roboflow dataset reports mAP@50 of 57.7% on their own evaluation. With merged data and default augmentation, we expect similar.
- **Localisation ceiling:** With bbox-derived corners, translation error floor is ~2-3cm at close range (1-3m) and ~8-12cm at long range (6-8m). Rotation is more robust due to PnP's angular stability.
- **What would raise it:**
  1. **Keypoint annotations** — Labelling 4 corners per pallet and training YOLOv8-pose would reduce corner error from ~10px to ~2px, likely bringing translation error to sub-2cm at close range.
  2. **More images from the deployment camera** — Images captured at 1.2m height, 20° tilt would match inference conditions.
  3. **Higher-resolution images** — Current images may be low-res; 1080p+ would improve corner precision.
  4. **Domain adaptation** — Fine-tuning on a small set of real warehouse images from the deployment camera.
  5. **Synthetic augmentation** — Generating pallet images with known poses using Blender/Unity to expand training data.

## Known Biases and Gaps

1. **Camera angle mismatch:** Source images are not captured from a 1.2m height, 20° tilt camera. This affects pose estimation accuracy at inference time.
2. **Pallet type:** Dataset may contain mixed pallet types (EUR, GMA, plastic, wood). We assume standard EUR (1.2m × 0.8m) for pose — source of error for non-EUR pallets.
3. **Lighting:** Indoor warehouse lighting varies; no controlled lighting in source data.
4. **Occlusion:** Some pallets in the dataset may be partially occluded by other pallets or equipment.
5. **Load diversity:** Limited variety in load types (boxes, wrap colours, box sizes).
6. **Geographic bias:** Images may not be from Indian warehouses, where pallet types, box styles, and warehouse layouts may differ.
7. **No depth data:** No RGB-D or LiDAR data available; all depth must be inferred from monocular geometry.
8. **No keypoint annotations:** The biggest gap — bbox-only labels prevent training a true keypoint detection model. Corners are estimated, not detected.
9. **Small dataset size:** 519 images is small for object detection. Typical production datasets have 5,000+ images.
10. **Single class:** Only `pallet` is annotated. No `box`, `stretch_wrap`, or `damage` classes for load analysis — SOP checks rely on heuristics instead.
